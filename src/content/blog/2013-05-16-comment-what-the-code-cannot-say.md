<p>Here&#8217;s a great explanation from &#8220;97 things every developer should know&#8221;</p>
<blockquote><p>Comments should say something code does not and cannot say. A comment explaining what a piece of code should already say is an invitation to change code structure or coding conventions so the code speaks for itself. Instead of compensating for poor method or class names, rename them. Instead of commenting sections in long functions, extract smaller functions whose names capture the former sections’ intent. Try to express as much as possible through code. Any shortfall between what you can express in code and what you would like to express in total becomes a plausible candidate for a useful comment. <strong><em>Comment what the code cannot say, not simply what it does not say.</em></strong></p>
</blockquote>
<p><em>Emphasis mine</em></p>
<p>Interestingly the previous page argues comments are exceptionally useful especially considering the JavaDoc generation- dare I say it, I think I agree. Countless times I&#8217;ve used a very well written API which was accompanied with a great JavaDoc. I&#8217;d usually consider this a crime against software engineers everywhere but an API which shall remain nameless included a code example &#8211; that saved me a lot of time! </p>
